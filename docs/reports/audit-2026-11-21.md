## 3. Root causes of the problems you reported

| # | Symptom | Root cause (evidence) | State |
|---|---|---|---|
| 1 | Message to Vimal "failed", nothing on LinkedIn | `pages.connection_state()` read buttons only inside a guessed header selector (`main section:first-of-type`) and returned `not_connected` when it did not find the Message link, so `actions.send_message` returned `NOT_CONNECTED` before clicking anything. Worker log line "connection check read not_connected; header buttons: ..." is written for this. Rows: `agent_tasks` 3da4e460, 6d7bc154 (result `not_connected`, `committed_at` empty = page never touched). Then `outreach_results._message` treated a known connection as an error: first as retry, then as `failed`. | Selector fix is in `d964854` (commit says verified on one 1st-degree profile). **Not verified by me**: no real send attempted, needs your OK. |
| 2 | Leads 3, Invites 3, Accepted 2 on "my connections" | Stats were derived from lead status (a connections lead is already `connected`), so every lead looked invited and accepted. | Fixed before my audit (`campaign_stats` now counts real tasks). Seen on screen: 0 and 0. |
| 3 | Existing connections show "connection request sent / waiting" | **Not reproduced** in today's data (3 clean runs, no `send_invite` task). Code paths that can produce it: `outreach_results._invite` maps `already_pending` to lead status `contacted`, and `_check` keeps a run in `waiting_connection` when the page reads `not_connected` for someone who is a connection (the same wrong header read as problem 1). `already_connected()` only holds for these leads through `connection_degree == 1` and `status == connected`, because `audience_source` is the string `'null'` (issue 9). | Open: depends on issues 1 and 9. |
| 4 | Every timestamp "Saturday 11th, 6 a.m." | Two causes found. (a) `LiveProfilePages._read_open_thread` stamps every message with `datetime.now()` of the read (pages.py line 681), so every inbox message in a sync shares one time. (b) `routers/campaigns._monitor` returned naive datetimes via `.isoformat()` (SQLite drops the zone), which a browser reads as local time. I could not reproduce the exact "Saturday 11th, 6 a.m." string anywhere in the frontend code (no date-fns pattern produces "11th"), so that exact text is **not verified**; it is very likely LinkedIn's own thread heading that the screenshot compared against. | (a) not fixed, needs a real DOM capture. (b) fixed. |
| 5 | Vimal, Pandey, K show a message step after "accepted" though already connected | **Not reproduced**: today's DB has no such rows. A repair of old leads was done earlier (`synex.db.bak-before-lead-repair-20261120` exists). The reply-to-acceptance path in section 4 (issue 3) and the header misread can both give a false "accepted". | Not verified. |

## 4. New problems found (with evidence)

| # | Area | What is wrong | Severity | Fix | Status |

| 1 | Engine | `_emit_for_run` set the run to `awaiting_agent` for 24 h even when no task was queued (idempotency key kept by a `failed` task, or no room). Run sat invisible and "In progress". Seen: run 76c74821 `awaiting_agent`, next_action +24 h, no task row. | High | Look at why nothing was queued: done -> move on, failed -> stop with `send_failed`, no room -> retry in 1 h. | **Fixed**, test `StuckRunTest` |
| 2 | Inbox sync | Reads share the sender's `sync_inbox` budget (Meet Affix: 12/day) but ran every 15 min, so the budget was gone in 3 hours and no reply could be seen for the other 21 h, silently. | High | Space reads at 24 h / budget. | **Fixed**, test `InboxBudgetTest` |

Real fix: read the real time from the page. |
